--- LOP-033 [✓] Architektur: Seam vs. Cut (Gesamtbild) — GEKLÄRT -----------

  Kategorie: Architektur / Datenmodell
  Status: GEKLÄRT (Mai 2026) — Entscheidung und Pfadkatalog dokumentiert;
  keine offene Architektur-Unklarheit mehr. Restarbeit nur in Unter-LOPs.
  Übergeordnet zu: LOP-009, LOP-010, LOP-016 (technische Restarbeiten)
  Referenz: docs/SEAM-VS-CUT-ZUORDNUNG.txt (Pfadkatalog, Mai 2026 abgeglichen)

  Entscheidung (Projektregel, codebase-verifiziert Mai 2026):
  ┌──────────────────────────────────────────────────────────────────────────┐
  │ Nahtzugabe gesetzt UND seamLine geschlossen (length >= 3)                │
  │   → Bearbeitungs-Master = seamLine (Seam-as-Master)                    │
  │   → cutLine wird bei jeder Änderung vollständig per Offset neu erzeugt   │
  │     (deriveCutLineForPiece); kein segmentweises seam↔cut-Mapping.      │
  │ Sonst (keine NZ oder seamLine zu kurz)                                   │
  │   → Bearbeitungs-Master = cutLine; seamLine ggf. aus cut abgeleitet.   │
  └──────────────────────────────────────────────────────────────────────────┘
  Eine Quelle der Wahrheit für die Bearbeitungs-Master-Entscheid:
  useSeamLineForVertexEditing() in src/geometry/vertexMaster.ts
  (identisch: getCurvesForSeamEdge / getEditingContour in seamUtils.ts).

  UI / Hit-Tests (keine parallele Master-Kontur):
  • WorkspaceCanvas: Vertices, Hover, Marquee, Kantenwerkzeuge →
    useSeamLineForVertexEditing + getDisplayedMasterCurves (gerundete Bögen).
  • Nahtzuordnung (SeamAssignment.curveIndices) → getCurvesForSeamEdge
    (bei NZ = seamLine-Indizes).

  Bewusst cutLine-zentriert (andere Domäne, kein Bearbeitungs-Bug):
  • Kerben: vertexIndex, Abstand/Kollision, materialize/resync entlang cutLine
    (notchOnCurve.ts, resyncNotchesAfterCutLineRebuilt nach jedem Cut-Rebuild).
  • Export/Cutter: Außenkontur aus cutLine (DXF-MASTER, AAMA/ASTM Layer CUT).
  • Fadenlauf-Snap, Bounds/pieceTransform: cutLine.
  • Konturmaße: eigener Schalter useSeamLineForContourMeasurements
    (contourMeasurements.ts) — nur wenn cutLine feiner tesselliert ist als
    seamLine; absichtlich ≠ vertexMaster, damit Maßlabels nicht jedes
    Clipper-Mikrosegment listen.

  Umgesetzt (Auszug, siehe SEAM-VS-CUT-ZUORDNUNG.txt):
  ✓ Store-Kern: updateVertex, updateCurvePoint, insertPointOnCutLine,
    offsetSegment, replaceSegmentWithBezier, movePointOnCurve, convertBezier…,
    applyOffset, recomputeSeamLine (Skip bei Seam-Master), scalePieceLocal,
    flipPieceAlongGrain, applyPieceSymmetryToPiece.
  ✓ LOP-057: softVertices/remap nach Cut-Rebuild (kein Index-Copy mehr).
  ✓ removeNotch: nur Notch-Liste; removeNotchAnchor/toggleNotchAnchor No-Ops.

  Restarbeit (nur noch in Unter-LOPs, nicht LOP-033):
  • LOP-016: addCurveToCutLine schreibt nur cutLine (Digitalisierung ohne NZ).
  • LOP-009/010: Notch-Typ-Mapping und cutLine-vertexIndex / Resync.
  • LOP-021: Produkt (mehr Notch-Typen; ggf. Master-Index später).

  Empfehlung für neue Features (Regel bleibt gültig):
  Keine zweite Bearbeitungs-Wahrheit in UI und Store — dieselbe Master-Kontur
  wie bei Hit-Tests (getDisplayedMasterCurves / getCurvesForSeamEdge).

--- LOP-070 [ ] UX-Vision: Canvas-first, Intent statt Tool-Wüste -----------

  Kategorie: Produkt / UX-Richtung (strategisch; Features bleiben, Präsentation
  und Aktivierung ändern)

  Ausgangslage (ehrliche Einordnung):
  • Funktional stark, kognitiv eher Power-Tool (viele Menüs, Werkzeuge, Leisten).
  • Risiko: neue Nutzer überfordert, nur Experten bleiben; UI wirkt „mächtig
    aber stressig“.

  Grundprinzip:
  • Weg von „viele Buttons = viele Tools“ hin zu „ein Canvas – Kontext entscheidet“.
  • Apple-nah heißt hier: 1 Hauptinteraktion, 1 sekundäre, Rest nur bei Bedarf
    (progressive disclosure), nicht zwangsläufig Features streichen.

  Zielbild A — Drei Hauptmodi statt vieler permanenter Werkzeuge
  1) Erstellen: Klick/Drag erzeugt sinnvolle Defaults; Kontext (leere Fläche vs.
     Kante vs. Linie) steuert, ob Teil, Punkt, Kerbe, Kontur folgt — weniger
     explizites Werkzeugwechseln.
  2) Bearbeiten: direkte Manipulation (ziehen, drehen, Snap); Doppelklick = Detail;
     idealerweise weniger Modus-Wechsel nur zum Verschieben eines Punkts.
  3) Naht / Technik: Nahtzugabe, Kerben, Bohrungen, Zuordnung — alles, was

--- LOP-057 [✓] Bug: Harte Vertices → soft bei Seam-CutLine-Rebuild ----ERLEDIGT

  Kategorie: Bug / Datenintegrität [!]
  Status: ERLEDIGT (April 2026)

  Problem:
  Bei Seam-as-Master wird die cutLine per Offset aus der seamLine abgeleitet.
  Die neue cutLine hat ggf. andere Vertex-Positionen (Clipper-Offset). An 6
  Stellen im Store wurde die alte softVertices-Liste per Index-Range-Filter
  (.filter(vi < cutLine.length)) auf die neue cutLine übertragen – ohne
  geometrisches Remapping. Index i auf der alten cutLine ≠ Index i auf der
  neuen cutLine → harte Vertices (rot) landeten an falschen Indizes und
  wurden als soft (blau) interpretiert.

  Betroffene Store-Aktionen:
  1. updateCurveSegment (Seam-as-Master-Zweig)
  2. insertPointOnCutLine (Seam-as-Master-Zweig)
  3. replaceSegmentWithBezier (Seam-as-Master-Zweig)
  4. movePointOnCurve (Seam-as-Master-Zweig)
  5. convertBezierSegmentToLine (Seam-as-Master-Zweig)
  6. offsetSegment (Seam-as-Master-Zweig)

  Lösung (Phase 1 – Store-Remap):
  Alle 6 Stellen: .filter() ersetzt durch remapSoftVerticesToNewCutLine(),
  das per Positions-Matching (nearestCutVertexIndex) die soft-Indizes
  korrekt auf die neue cutLine überträgt.

  Lösung (Phase 2 – Display-Mapping + Threshold):
  Problem war noch nicht vollständig gelöst: masterSoftVertexIndexSet() in
  seamUtils.ts hatte einen Fallback (Cut-Soft → nächster Master) OHNE
  Distanzschwelle. Orphane Cut-Soft-Indizes wurden auf beliebige harte
  Master-Vertices projiziert → harte Eckpunkte erschienen blau.
  Zusätzlich: nearestCutVertexIndex in remapSoftVerticesToNewCutLine hatte
  ebenfalls keine Schwelle → bei Topologie-Änderung durch Clipper konnten
  alte Soft-Positionen auf beliebige neue Vertices gemappt werden.

  Fix Phase 2:
  ✓ masterSoftVertexIndexSet: Fallback nutzt jetzt Schwelle
    max(seamAllowanceMm×3, MAP_CUT_TO_MASTER_EPS_MM×2)
  ✓ nearestCutVertexIndex: optionaler maxDistMm-Parameter
  ✓ remapSoftVerticesToNewCutLine: nutzt REMAP_MAX_DIST_MM = 50mm

  Fix Phase 3 (April 2026 – endgültige Behebung):
  Problem: Phase-2-Schwelle war nicht ausreichend. Clipper entfernt kollineare
  Vertices (z. B. eingefügter Punkt auf gerader Kante), sodass kein Cut-Vertex
  nahe dem Master-Vertex existiert. syncSoftAfterSharpCornerPromotion filterte
  softVerticesMaster per Cut-Mapping → Master-Soft-Eintrag verschwand. Zusätzlich
  mappte masterSoftVertexIndexSet verwaiste Cut-Soft-Indizes zurück auf harte
  Master-Vertices.
  ✓ mapMasterVertexIndexToCutVertexIndex: Distanzschwelle max(seamAllowanceMm×2, 8)
  ✓ mapCutVertexIndexToMasterVertexIndexForVertexDrag: Distanzschwelle analog
  ✓ syncSoftAfterSharpCornerPromotion: softVerticesMaster NUR per Range-Check
    validiert (m >= 0 && m < seamLine.length), NICHT mehr per Cut-Mapping gefiltert.
    Grund: softVerticesMaster ist die alleinige Quelle der Wahrheit.
  ✓ masterSoftVertexIndexSet: Für seam-as-master NUR softVerticesMaster verwenden.
    Kein Rück-Mapping von softVertices (Cut-Indizes) → Master, weil verwaiste
    Cut-Indizes sonst fälschlich auf harte Master-Vertices projiziert werden.
  ✓ insertPointOnCutLine: nearestCutVertexIndex mit maxDist-Schwelle aufgerufen
    max(seamAllowanceMm×3, 20), damit verwaiste Seam-Punkte nicht auf weit
    entfernte Cut-Corner gemappt werden.

  Test: softVertexStability.test.ts (5 Tests, inkl. masterSoftVertexIndexSet-
  Prüfung nach Punkt-Einfügen und nach mehrfachem Einfügen).
