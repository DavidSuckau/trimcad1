--- LOP-043 [ ] WorkspaceCanvas: 6.300-Zeilen-Monolith ---------------------

  Kategorie: Architektur / Wartbarkeit
  Problem:
  WorkspaceCanvas.tsx (~6.292 Zeilen) enthält: Domain-Mathematik, Hit-Testing,
  Koordinaten-Transforms, komplette Editor-UX, SVG-Rendering, Pointer-Events,
  Keyboard-Handling, Overlays/Popover, PieceGroup-Komponente.
  • Testbarkeit nahezu null (keine Unit-Tests für Canvas-Logik)
  • Review/Merge extrem aufwändig
  • HMR und Bundle-Size leiden
  • PieceGroup (~500 Zeilen) ist intern definiert, nicht memo-isiert
  • Schwere Nutzung von IIFEs in JSX (z. B. ~Zeile 1114–1200, 4852+)

  Empfehlung:
  Schrittweise aufteilen: PieceGroup → eigene Datei; Pointer-Hooks → eigene
  Hooks; Hit-Testing/Koordinaten → utility; Keyboard-Handler → eigener Hook.
  Aufwand: hoch. Impact: langfristig Wartbarkeit, Testbarkeit.


--- LOP-044 [ ] useStore: 2.620-Zeilen-Monolith ----------------------------

  Kategorie: Architektur / Wartbarkeit
  Problem:
  Alle Actions, State-Felder, Hilfsfunktionen in einer Datei (~2.620 Zeilen).
  Store-Interface (~Zeile 276–516), freie Helpers (~65–634), Implementierung
  (~636–2619).

  Empfehlung:
  In Zustand-Slices aufteilen (z. B. workspaceSlice, pieceGeometrySlice,
  seamSlice, uiSlice, digitizeSlice). Pure Helpers (deriveCutLineForPiece,
  adjustSeamAfterInsert, mergeAdjacentSegments, digitizeNodesToCurves) in
  eigene Module auslagern. Store-Interface exportieren.
  Aufwand: hoch. Impact: Wartbarkeit, Review, Merge-Konflikte.


--- LOP-045 [ ] [!] Performance: Breite Store-Subscriptions + kein memo -----

  Kategorie: Performance
  Problem:
  WorkspaceCanvas (~1283–1385), Sidebar (~4), DesignBar (~4–15), Toolbar (~61+)
  ziehen viele Felder ohne Selektoren aus dem Store (useStore() statt
  useStore(s => s.field)). Jede Store-Änderung triggert Re-Renders dieser
  großen Komponenten.
  Zusätzlich: PieceGroup hat kein React.memo; Inline-Handler in pieces.map
  (~4769–4831) erzeugen bei jedem Render neue Funktions-Instanzen.
  handlePointerMove useCallback (~2979–3107) hat große Dependency-Liste,
  Identity wechselt häufig.

  Empfehlung:
  1. Granulare Selektoren einführen (useStore(s => s.pieces) etc.)
  2. PieceGroup mit React.memo wrappen
  3. Inline-Handler durch useCallback oder stabile Referenzen ersetzen
  Aufwand: mittel. Impact: massive Performance-Verbesserung.

--- LOP-051 [ ] Accessibility-Mängel (Modals, Sidebar, Canvas) --------------

  Kategorie: Accessibility / UX
  Problem:
  • Canvas (WorkspaceCanvas): kein role, kein aria-label, keine
    Focus-Verwaltung für Screen-Reader.
  • Sidebar (~12–16): <li onClick> ohne tabIndex / role="button" → nicht
    per Tastatur bedienbar.
  • Context-Menus: role="menu" aber Buttons ohne role="menuitem", keine
    Pfeiltasten-Navigation.
  • Modale: inkonsistent – HelpModal hat korrektes role="dialog" + aria-modal,
    aber MassstabModal, SeamAssignmentMetaModal, ConfiguratorModal fehlen diese.
  • DesignBar: kein aria auf dem footer-Gruppencontainer.

  Empfehlung:
  Langfristig ARIA-Pattern für Modals, Menüs und Sidebar vereinheitlichen.
  Kurzfristig: Sidebar-Rows focusbar machen, Modal-role konsistent setzen.
  Aufwand: mittel. Impact: Barrierefreiheit, ggf. gesetzliche Anforderungen.

--- LOP-053 [ ] Performance: Keyboard-useEffect + Listener-Churn -----------

  Kategorie: Performance
  Problem:
  WorkspaceCanvas Global-Keyboard-Handler (~Zeile 3222–3690): sehr großes
  Dependency-Array mit häufig wechselnden Werten (pieces, hovered*, dragging,
  cutSeamSwappedSet etc.). Der document-Listener wird bei fast jeder
  Interaktion neu registriert (remove + add).
  Mehrere separate useEffects registrieren document-Level-Listener
  (pointerdown, auxclick, keydown) → hohe Gesamt-Listener-Anzahl.

  Empfehlung:
  Refs für aktuellen State statt Dependencies; oder ein einzelner stabiler
  Dispatcher mit Ref-basiertem Zugriff. Listener-Konsolidierung.
  Aufwand: mittel. Impact: weniger Event-Churn bei aktiver Nutzung.


--- LOP-055 [ ] Batch-Actions: Mehrfach-set() statt gebündelt ---------------

  Kategorie: Performance / Korrektheit
  Problem:
  batchSetVerticesSoft (~827–832), batchDeleteFiltered (~835–889),
  batchDeleteMarqueeCompletePieces (~892–915), snapSeamEdgeToMatch (~1401),
  rotatePiece90 (~2339–2340), alignPieceToGrain (~2352–2388),
  regenerateConfiguratorPart (~995–1023) – alle feuern mehrere separate
  set()/get().action()-Aufrufe. Logisch eine User-Operation, aber:
  • N Subscriber-Notifications / React-Re-Renders
  • Zwischenstände existieren (inkonsistenter State zwischen Iterations)
  • Fragil bei zukünftiger Middleware oder Async

  Empfehlung:
  Zusammenfassende set()-Aufrufe wo möglich; oder Zustand batch-Middleware.
  Aufwand: mittel.


--- LOP-056 [~] React-Patterns: Index-Keys, Popover-Sync, Viewbox-Konst. ---

  Kategorie: React-Patterns / Kosmetik

  Erledigt (April 2026):
  ✓ Toter Code _projectOntoSegment + void-Silencer aus WorkspaceCanvas entfernt
  ✓ Deprecated seamVertexNearProjectedNotch aus notchResyncCutLine entfernt

  Noch offen:
  1. Index-Keys wo Listen sich ändern können: Digitize-Preview
     key={`dig-pt-${i}`}, NotchSettings key={i},
     RockGeneratorModal dart lines key={idx}.
  2. EdgeAllowancePopover: useEffect(…, []) läuft nur bei Mount; wenn Popover
     gemountet bleibt und popover.currentMm wechselt, kann lokaler value-State
     veraltet sein.
  3. Doppelte Viewbox-Konstanten: VIEWBOX_CX/CY in Toolbar.tsx getrennt von
     VIEWBOX_WIDTH/HEIGHT in WorkspaceCanvas → zwei Quellen der Wahrheit.
  4. @ts-expect-error in offset.ts für clipper-lib umgeht TS-Safety.

  Empfehlung:
  Keys auf stabile IDs umstellen; Popover key von pieceId+edgeIndex;
  Viewbox-Konstanten zentralisieren.
  Aufwand: gering–mittel.
