--------------------------------------------------------------------------------
LEITBILD: WAS EIN MAUSMOVE HEUTE OFT TUT vs. ZIEL
--------------------------------------------------------------------------------

Heute (typisches Anti-Pattern — je nach Pfad unterschiedlich stark):

  mousemove
     ↓
  React / Zustand
     ↓
  Workspace neu berechnen / referenzieren
     ↓
  alle Pieces durchlaufen
     ↓
  Hit-Tests (Piece, Segment, Seam, Notch, Pivot, …)
     ↓
  Bézier nearestOnCurve
     ↓
  Notches / Seam-Prüfung
     ↓
  SVG aktualisieren

Ziel:

  mousemove
     ↓
  letzte Position merken
     ↓
  requestAnimationFrame (max. ~1× pro Frame)
     ↓
  nur relevante Hit-Tests (Mode-Gate)
     ↓
  nur betroffene UI aktualisieren (Render-Isolation)

--------------------------------------------------------------------------------
PHASE 0 — PROFILING ZUERST (30–60 Minuten)
--------------------------------------------------------------------------------
Ohne Messung raten wir. Vor jeder größeren Code-Änderung einmal Baseline.

Szenarien:
  A) 5 Teile, wenig Kerben
  B) 20 Teile + viele Zuordnungen + Prüfanzeigen an
  C) 1 komplexes Teil + 50+ Kerben (inkl. Ease)

Je Szenario Aktionen:
  - Hover (leer über Fläche / über Kontur)
  - Piece verschieben
  - Vertex verschieben
  - Naht-Hover / Prüfanzeige
  - Zoom / Pan

Metriken (Chrome Performance + React Profiler; optional performance.mark):
  - Frame time (ms)
  - JS execution time
  - React render time
  - Hit-test time
  - Path generation time

Beispiel-Erkenntnis (Ziel der Messung):
  Hover = 22 ms
    davon Hit-Test = 15 ms
    React         =  4 ms
    SVG           =  3 ms
  → Dann klar: zuerst Hit-Test, nicht SVG.

Ergebnisse kurz hier oder in einem Anhang notieren (Datum, Browser, Gerät).


--------------------------------------------------------------------------------
1) POINTER / HIT-TESTS (Phase A — nach Profiling)
--------------------------------------------------------------------------------

1.1 Pointer rAF-Throttle (bester erster Code-Schritt)
    Problem: 150–300 mousemove/s → jede Bewegung triggert teure Hits.
    Lösung:
      Pointer-Events → letzte Position speichern → ein rAF → Hit-Test
    → praktisch max. ~60–120 Berechnungen/s statt jede Bewegung.
    Wichtig: Drag nicht unnötig ausbremsen (Piece-Drag ist schon rAF).
    Neuer Throttle betrifft vor allem Hover / Hit-Test, nicht Commit-Logik.
    Datei: WorkspaceCanvas.tsx

1.2 Mode-Gate Hit-Tests (extrem günstiger Gewinn)
    Beim Piece-Verschieben nicht alles prüfen:
      Piece + Segment + Seam + Notch + Pivot + Profile + Measurement …
    Sondern je Tool/Modus nur das Nötige, z. B.:
      SELECT      → Piece-Hit (ggf. Notch wenn Kontur-Edit)
      SEAM TOOL   → Seam-Hit
      NOTCH TOOL  → Notch-Hit
      VERTEX TOOL → Vertex-Hit
    Frühabbruch + klare Mode-Tabelle.

1.3 nearestOnCurve entschärfen (Architektur)
    Pointer → AABB → Kandidaten → grobes Bézier-Sampling
         → nur bei echtem Treffer feines Sampling / Refine
    Hover: grob; Drag-Snap / Commit: fein.
    Segment-AABB: Kurve skippen wenn weit weg.

1.4 Notch-Hover vereinfachen
    Nicht sofort volle Cutout-Geometrie bauen.
    Zuerst Distanz zum Anker / Strich; Cutout nur wenn nah genug.

1.5 piecesById flächendeckend
    Alle pieces.find im Canvas ersetzen — geringer Aufwand, sauber.


--------------------------------------------------------------------------------
2) REACT RENDER-ISOLATION (Phase B — oft der größte Hebel)
--------------------------------------------------------------------------------

Kernproblem heute (sinngemäß):

  Piece 17 ändert Transform
       ↓
  workspace ändert sich
       ↓
  Canvas rendert
       ↓
  viele/alle Pieces bekommen neue Props

Ziel:

  Piece 17 ändert sich → nur Piece 17 (+ ggf. Overlay 17) neu
  Piece 1…16, 18…n    → bleiben (memo hält)

2.1 Granulare Store-Selektoren / Drag-Preview
    - Nicht das ganze `workspace` an den Canvas hängen.
    - Beim Verschieben: lokale Preview-Transform oder nur bewegtes Teil
      invalidieren; unbewegte PieceGroups unberührt lassen.

2.2 PieceGroup stabilisieren (Memo wirklich wirksam)
    - Inline-Handler im pieces.map → neue Funktions-Props → memo wirkungslos.
    - Stabile Handler (Ref + pieceId) oder Context.
    - Props möglichst Primives / stabile Referenzen.

2.3 Revision / Fingerprint (danach)
    - geomEpoch / transformEpoch / notchEpoch
    - memo vergleicht Epochs statt tiefer Objektgleichheit.

2.4 Canvas-Monolith splitten
    - Hoher Aufwand, Wirkung erst nach A/B — noch nicht priorisieren.
    - Später Wartbarkeit (LOP-043), nicht als erster Perf-Hebel.


--------------------------------------------------------------------------------
3) PATH-CACHE, CULLING, LOD (nach A/B bzw. wenn Messung es zeigt)
--------------------------------------------------------------------------------

3.1 Path-Cache (sehr sinnvoll)
    Geometrie ≠ Transform ≠ View.
    Cache-Key ungefähr:
      pieceId + geomEpoch + notchEpoch + displayMode
    NICHT an: zoom, pan, pointerPosition.
    Verschieben/Zoomen darf Konturpfade nicht neu erzeugen
    (Transform bleibt SVG-group-Attribut).

3.2 LOD Kerben (später)
    Zoom-out / DRAGGING: einfache Striche statt voller Cutouts.

3.3 Viewport-Culling
    Teile außerhalb der ViewBox nicht voll mounten (oder AABB-Platzhalter).
    Besonders bei großen Projekten.

3.4 SVG-Node-Budget
    Ease/Maße/Prüfanzeigen: Cluster, Hover-only, oder während Drag aus.

3.5 WebGL / Hybrid
    VORERST VERGESSEN.
    Erst: Throttle → Hit-Test → React → Cache → Culling → LOD.
    Nur wenn danach noch nicht reicht: Hybrid diskutieren.


--------------------------------------------------------------------------------
4) GEOMETRIE WÄHREND DRAG (Phase C — Spikes)
--------------------------------------------------------------------------------

4.1 Offset während Drag vereinfachen
    Vertex-Drag: grobe Preview / Seam-only; voller Clipper am Ende.

4.2 Tessellation staffeln
    Drag grob (16–24), Final/Export fein (64+).

4.3 Notch-Resync entkoppeln
    Nicht jedes Pointer-Event; Drag-Ende oder gedrosselt — wenn Profiler Spikes zeigt.

4.4 Worker
    Nur wirklich schwere Jobs (großes Offset, Massen-Resync, …).
    Nesting ist schon Worker. Serialisierung beachten.

4.5 Batch-Store-Updates (LOP-055 Rest)
    Eine Aktion = ein set().


--------------------------------------------------------------------------------
5) INTERACTION QUALITY LEVELS (Ergänzung — sehr CAD-typisch)
--------------------------------------------------------------------------------
Nicht nur ein manueller „Performance-Schalter“, sondern automatisch
während aktiver Interaktion herunterregeln:

  NORMAL (Idle / Hover ruhig)
    ├─ volle Konturen
    ├─ Kerben (voll)
    ├─ Prüfanzeigen (wenn eingeschaltet)
    ├─ Maße (wenn eingeschaltet)
    └─ Hover-Hits (bereits rAF + Mode-Gate)

  DRAGGING (Piece / Vertex / Notch-Move aktiv)
    ├─ Konturen
    ├─ vereinfachte Kerben (LOD)
    ├─ keine teuren Prüfanzeigen / Seam-Metriken live
    ├─ vereinfachtes Bézier (grobes Sampling)
    └─ Ziel: „Wo ist mein Teil gerade?“ — nicht jede Nebenrechnung

  IDLE (nach Loslassen)
    └─ alles wieder vollständig (ein Commit-Pass)

Begründung: Während des Ziehens braucht der Nutzer Lage-Feedback,
nicht gleichzeitige Nahtprüfung + alle Maße + volle Kerbengeometrie.

Dazu optional manueller Performance-Modus (5.5):
  Prüfanzeigen aus, Maße aus, aggressiverer Throttle, LOD dauerhaft —
  für Demos / große Lederprojekte.

--------------------------------------------------------------------------------
8) WAS WIR BEWUSST NICHT ALS ERSTE LÖSUNG SEHEN
--------------------------------------------------------------------------------
- SVG allein „schneller machen“, während mousemove die ganze Pipeline triggert
- Server-seitiges Rendering der Arbeitsfläche
- Alles auf WebGL umschreiben, bevor Throttle/Hit/React/Cache/Culling/LOD ausgereizt
- Canvas-Monolith splitten nur wegen Perf (zu teuer zuerst)
- Aggressive Memoization ohne Profiler (falsche Props → null Effekt)
- Mehr Caching als Ersatz für weniger Arbeit pro Event
